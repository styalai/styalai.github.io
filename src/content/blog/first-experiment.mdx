Learning rate is the first hyperparameter everyone sets and the last one anyone
explains. I wanted a page I could point at when the subject comes up, so this is
a small, deliberately boring experiment: three learning rates, one fixed seed,
sixty steps, and a loss curve for each.

One warning before the results, because it would be easy to misread them: **the
curves in this post are synthetic.** They are generated by
`src/data/make-training-losses.mjs`, which is checked in next to the data, so you
can read exactly how they were produced. No model was trained to produce them.
The point is to show what a learning-rate sweep *looks like* and to give myself a
template for writing up the real version later.

## Setup

The quantity being tracked is the usual next-token cross-entropy loss. Writing
$\hat{p}_\theta(x_t \mid x_{<t})$ for the model's predicted distribution over the
vocabulary $V$ at position $t$, and $y_t$ for the one-hot target, the per-token
mean is

$$
\mathcal{L}(\theta) = -\frac{1}{N}\sum_{i=1}^{N}\sum_{t=1}^{|V|} y_{i,t}\,\log \hat{p}_\theta(x_{i,t} \mid x_{i,<t})
$$

where $N$ is the number of tokens in the batch. Values are in nats per token, so
a loss of $3.4$ corresponds to roughly uniform predictions over a vocabulary of
about $e^{3.4} \approx 30$ tokens. That is roughly where these runs start.

The runs themselves differ only in the step size $\eta$ used by the plain SGD
update

$$
\theta_{t+1} \;=\; \theta_t \;-\; \eta\,\nabla_\theta \mathcal{L}(\theta_t)
$$

with no momentum, no weight decay, no warmup, and a fixed batch size. Everything
else is held constant, which is the entire point: one variable, three values.

| Run | Learning rate $\eta$ | Steps | Notes |
| --- | --- | --- | --- |
| A | `1e-3` | 60 | conservative |
| B | `3e-3` | 60 | middle of the sweep |
| C | `1e-2` | 60 | aggressive |

## What I think is going on

Nothing exotic, and I want to be careful not to over-claim from synthetic data.
The reading I would expect, and which is at least consistent with the shape
here, is ordinary:

- Below roughly $10^{-2}$ the step is small enough that the parameters move
  smoothly, so the loss curve is a slow, boring, monotonic descent. That is run A.
- Somewhere in between, the step is large enough to cover ground quickly and
  small enough that gradient noise averages out across the batch. That is run B.
- Above that, each step overshoots. The loss does not diverge — it wanders,
  hovering near a floor it cannot quite settle onto. Run C's gap between best
  and final loss is the signature of that.

The general shape — a stable region, a sweet spot, an unstable region — is not a
finding. The useful observation is narrower: *the same sweep measured only by
final loss would have rated run C ahead of run A*, when the gap column shows run
C spent most of its budget oscillating. Final-loss-only comparisons quietly
reward lucky runs.

## Limitations

This is a small experiment and most of what makes it interesting is what it does
not do:

- **The data is simulated.** Every number here comes from a generator, not from a
  training run. Treat the shapes as a template, not as evidence about real models.
- **One seed, per configuration.** A single draw cannot separate "run B is better"
  from "run B got a lucky batch order". A real version needs three to five seeds
  per learning rate and error bars.
- **Sixty steps is very short.** Run A is almost certainly not converged. This
  sweep measures the first minute of training, not the end of it.
- **A single loss value is a narrow view.** Validation loss, gradient norm, and
  downstream task accuracy would all tell somewhat different stories, and the
  ranking between runs is not guaranteed to survive any of them.
- **No compute was spent**, which is convenient and also means there is nothing
  here about the wall-clock cost of any of this.
- **No interaction effects.** Batch size, warmup, and schedule all shift the
  stable region. A learning rate that is stable at batch size 32 may not be at
  512.

## Code

The training loop is unremarkable, which is the correct amount of unremarkable for
a first experiment. The part worth stealing is the loop that appends one row per
step to a JSON file, because writing results to a file you can hand to a plotting
script is what stops results from living and dying in a terminal scrollback.

```python
import json

STEPS = 60
LEARNING_RATES = [1e-3, 3e-3, 1e-2]


def train(lr: float, steps: int = STEPS) -> list[dict]:
    """Run plain SGD and return one record per step."""
    params = init_parameters(seed=1337)
    history = []

    for step in range(steps + 1):
        batch = next_batch()
        loss = cross_entropy(params, batch)
        # Recorded every step, including step 0, so the curve has its origin.
        history.append({"step": step, "loss": loss})
        params = params - lr * gradient(params, batch)

    return history


# Write results out rather than printing them. Same shape as the JSON the
# charts on this page consume, so the plotting code never has to change.
results = {
    "series": [
        {
            "lr": lr,
            "label": f"{lr:.0e}",
            "colorIndex": i,
            "points": train(lr),
        }
        for i, lr in enumerate(LEARNING_RATES)
    ]
}

with open("training-losses.json", "w") as handle:
    json.dump(results, handle, indent=2)
```

To run the real thing, drop your own numbers into
`src/data/training-losses.json` in the shape described in
`src/lib/chart-data.ts`. The charts do not care where the numbers came from, and
they will follow the theme and stay legible on a phone either way.
